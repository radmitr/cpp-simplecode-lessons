# 01. Предусловия, постусловия и проверки контракта

## Версия C++

Режим сборки — **C++26**, учебная конфигурация — GCC 16+. Версии отдельных механизмов отмечены в исходниках. Для C++26 реализация ещё может быть неполной.

## Что изучаем

Записываем требования функции рядом с её интерфейсом. Нужны функции, исключения и проверки входа.

## Примеры

- [main.cpp](main.cpp) — допустимые вызовы pre/post/contract_assert; результат `6`.
- [main2.cpp](main2.cpp) — наблюдение обработчика нарушения при семантике observe.

## Как это работает

`pre` проверяет требование до тела функции, `post(result: ...)` — результат после нормального завершения тела, `contract_assert` — условие в выбранной точке тела. Параметр `x` объявлен `const`, поскольку параметр по значению, используемый в постусловии, должен быть константным. В примере сначала проверяется положительность и ограничение аргумента, затем удваивается число, затем проверяется результат. Сборка GCC требует `-fcontracts`; маркер `language-feature.txt` передаёт флаг и в сборку, и в базу IntelliSense. Нарушение контракта не является обычным выбрасыванием исключения: дальнейшее поведение зависит от выбранной семантики.

## Сборка и запуск

[Настройка компилятора и запуск в VS Code](../../../README.md#сборка-и-запуск-в-vs-code).
Из корня проекта, Linux:

```bash
bash scripts/build-linux.sh bonus/contracts/01-contract-checks/main.cpp
./build/bonus/contracts/01-contract-checks/main
```

Для остальных вариантов замените `main.cpp` и имя исполняемого файла. На Windows вызовите `scripts/build-windows.sh` через MSYS2 Bash, затем соответствующий файл `build/bonus/contracts/01-contract-checks/main.exe`. Готовые `tasks.json` и `launch.json` содержат оба варианта системы.

Ввода, сетевых служб и постоянных файлов не требуется, если ниже не указано другое. Каждый пример проверяет результаты; успех — строка `OK modern-example` и код `0`, ошибка проверки — код `1`. `main2` без аргументов выполняет только допустимый вызов. Для нарушения требуется отдельная сборка с семантикой observe, описанная ниже.

В GCC семантика выбирается флагом `-fcontract-evaluation-semantic=`:

| Значение | Нарушение |
|---|---|
| `ignore` | Проверка не выполняется |
| `observe` | Вызывается обработчик, после его возврата выполнение продолжается |
| `enforce` | Обработчик, затем завершение программы |
| `quick_enforce` | Немедленное завершение без обработчика |

Наблюдаемый случай запускайте отдельно из корня на Linux:

```bash
/opt/gcc/16/bin/g++ -std=c++26 -fcontracts -fcontract-evaluation-semantic=observe bonus/contracts/01-contract-checks/main2.cpp -o build/contract-observe -Wl,-rpath,/opt/gcc/16/lib64
./build/contract-observe --violate
```

Ожидается `violations: 1` (реализация вправе организовывать проверки иначе, поэтому код принимает не меньше одного уведомления), затем `OK modern-example`. Функция только возвращает число: продолжение после нарушения не запускает опасную операцию. При `enforce`/`quick_enforce` тот же аргумент означает **намеренное аварийное завершение**, а не обычный успешный тест. В MinGW используйте аналогичный компилятор и путь вывода `.exe`.

## Типичные ошибки

Контракты не заменяют проверку недоверенного ввода. Не помещать в предикат необходимые побочные эффекты: при семантике `ignore` проверки отсутствуют. Нельзя считать, что наблюдаемое нарушение останавливает функцию. Для виртуальных интерфейсов и межфайловых сборок сверяйте ограничения реализации; здесь один исходник и обычная функция.
