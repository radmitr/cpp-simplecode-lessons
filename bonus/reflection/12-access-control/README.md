# 12. Контекст доступа и инкапсуляция

## Версия C++

`std::meta`, статическая рефлексия — **C++26**.
`auto`, `constexpr` — **C++11**.
`std::exception` — **C++98**.

Сборка примеров: **C++26**. Это режим проекта,
а не дата появления всех использованных конструкций.
Рефлексия здесь экспериментальная: нужны GCC 16+ и `-freflection`; конкретные требования заданы в файлах сборки.

## Что изучаем

Запрос списка и проверка доступности — разные действия. `unchecked`
позволяет получить метаданные без фильтрации по доступу. Сплайсинг уже полученного
отражения не выполняет повторную проверку доступа: `main.cpp` явно читает `private`-поле
через `unchecked`-список. При обычном прямом именовании ^^`Vault::secret` снаружи
класса доступ проверяется. current учитывает контекст запроса, unprivileged
фильтрует общедоступный интерфейс. Поэтому политика общего helper использует
unprivileged, а `unchecked` нельзя применять автоматически к сериализации.
`main2.cpp` отдельно показывает разрешённое прямое отражение из метода самого класса.

## Как это работает

Предварительно: Шаблоны, `constexpr`/`consteval` и предыдущие механизмы этого раздела.
Каждый исходник здесь — самостоятельный исполняемый пример.

`main` получает два поля `Vault` через `unchecked`. is_accessible отдельно
показывает: `visible` доступно непривилегированному коду, `secret` — нет.
Но сплайсинг уже полученного отражения `secret` всё же читает 2:
этому соответствует осознанный выбор `unchecked`.

main2 отражает `secret_` из метода самого `Vault`. Контекст current
соответствует этому месту и разрешает доступ без обхода внешней инкапсуляции.

Контекст — часть политики запроса, а не runtime-проверка пароля.
Для общих сериализаторов используйте открытый/разрешённый набор полей,
а не безусловный `unchecked`. Наличие технической возможности прочитать
`private` не означает, что поле стоит включать в публичный формат.

[Запуск в VS Code](../../../README.md#сборка-и-запуск-в-vs-code).

### Результат и проверка

После показанных в коде значений последняя строка — `OK 12-access-control`.
Проверки `check(...)` выбрасывают исключение при нарушении ожидаемого результата;
в таком случае программа печатает причину и возвращает 1. Они работают и с `NDEBUG`.
Адреса, диагностические имена типов, размеры и время могут отличаться между системами.
Проверка всего раздела: `python scripts/check-bonuses.py --section bonus/reflection`
(на Linux команда Python обычно называется python3).

## Типичные ошибки

### Самостоятельно

Добавьте `protected`-поле и проверьте его категорию. Сравните отказ прямого именования с разрешённым сплайсингом полученного `unchecked`-отражения.
