# 02. RTTI: `typeid`, `type_info` и `type_index`

## Версия C++

`std::type_index` — **C++11**.
`std::map`, `std::string`, `std::exception` — **C++98**.

Сборка примеров: **C++17**. Это режим проекта,
а не дата появления всех использованных конструкций.

## Что изучаем

RTTI — сведения о типе во время выполнения. Для полиморфного объекта,
доступного через ссылку, `typeid` сообщает его фактический (динамический) тип.
Полиморфный класс имеет хотя бы одну виртуальную функцию.
У самого указателя тип остаётся `Base*`. `type_index` позволяет использовать тип
как ключ контейнера. `name()` и `hash_code()` не подходят для устойчивого файлового
или сетевого идентификатора: их представление зависит от реализации. `typeid`
не перечисляет поля и методы. Разыменование нулевого указателя полиморфного типа
в операнде `typeid` может выбросить `bad_typeid`; не заменяйте проверку указателя этой операцией.

- [main.cpp](main.cpp).

## Как это работает

Нужны наследование, виртуальные функции, ссылки и `map`.

У `Base` есть виртуальный деструктор, поэтому `typeid(base)` при `Base&`
распознаёт фактический `Derived`. `typeid(&base)` исследует тип самого указателя
и остаётся `Base*`, не «заглядывая» автоматически через него.

`type_index` позволяет использовать результат как ключ `map`. Сравнивайте типы
через type_info/type_index, а не строки `name()`. Диагностическая строка зависит
от компилятора. `typeid` не перечисляет поля и не даёт их значения.
Для неполиморфного выражения обычный `typeid` не выполняет такой динамический выбор;
`typeid(*nullPolymorphicPointer)` — специальный ошибочный случай с bad_typeid.

## Типичные ошибки

Сравнивайте типы через `type_info`/`type_index`, а не через `name()`. Тип указателя и динамический тип объекта, на который он указывает, — разные запросы.

### Самостоятельно

Сравните `typeid` для полиморфной и неполиморфной базы. Сохраняйте соответствие типов через `type_index`, а отображаемые имена задайте отдельно.
