# 05. Время жизни параметров и захватов корутины

## Версия C++

C++20 — режим сборки; механизмы и даты их появления указаны в исходниках. Учебный компилятор — GCC 16+.

## Что изучаем

Различаем данные кадра и объекты, на которые он только ссылается. Нужны ссылки, лямбды и ленивый Task.

## Примеры

- [main.cpp](main.cpp) — самостоятельный пример; успешное завершение — код `0`.

## Как это работает

Параметр `std::string text` копируется/перемещается в кадр: временная строка
первого вызова может исчезнуть до `resume`, а данные кадра останутся живы.
Параметр `const std::string&` сохраняет только связь с `owner`. Изменение `owner`
до запуска видно корутине; уничтожать `owner` до завершения нельзя.

Захват лямбды хранится в объекте замыкания `closure`, а не автоматически копируется
в кадр её корутинного `operator()`. Поэтому `closure` объявлен до `third` и
живёт до завершения задачи. В конце области видимости объекты уничтожаются в
обратном порядке: задача раньше замыкания. Безымянная временная захватывающая
лямбда, уничтоженная сразу после вызова, могла бы оставить висячую ссылку.
Такой ошибочный пример не исполняется.

В четвёртом варианте лямбда ничего не захватывает, а строка передаётся явным
параметром по значению. Её данные принадлежат кадру. Аналогичная осторожность
нужна членам класса: использование `this` не продлевает жизнь объекта.
Ссылка, `string_view` и `span` внутри параметра по значению также не становятся
владельцами памяти. Сверяйте время жизни всех объектов, а не только самого Task.

Успех — `OK reference-example` и код `0`; ошибка проверки — код `1`.

## Типичные ошибки

Не считать любую передачу по значению глубокой копией: view по-прежнему ссылается на внешний буфер. Не уничтожать захватывающее замыкание, пока корутина читает его поля. Не проверять висячие ссылки запуском UB.
