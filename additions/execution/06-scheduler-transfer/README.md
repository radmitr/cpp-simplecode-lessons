# 06. Переключение планировщика

## Версия C++

C++26 — режим сборки; механизмы и даты их появления указаны в исходниках. Учебный компилятор — GCC 16+.

## Что изучаем

Переносим запуск и продолжение на два разных рабочих потока. Нужны run_loop и время жизни operation.

- [main.cpp](main.cpp) — самостоятельный пример; успешное завершение — код `0`.

## Как это работает

Каждый `Context` содержит цикл и обслуживающий его `jthread`. `starts_on` задаёт,
где начинается дочерний sender. Первый `then` проверяет ID первого потока и
превращает `20` в `21`. `continues_on` переносит дальнейшее завершение на второй
планировщик; следующий `then` проверяет второй ID и получает `42`.

`sync_wait` блокирует вызывающий поток до результата, а оба run_loop обслуживаются
своими потоками. Поэтому очередь не остаётся без исполнителя. Порядок проверяется
ID, а не задержкой. После результата деструктор каждого контекста вызывает
`finish()` и `join()`; только затем уничтожается сам loop. Ссылка scheduler не
должна переживать контекст, которому принадлежит очередь.

Планировщик описывает место/способ выполнения; перенос на другой поток происходит
здесь из-за выбранных run_loop, а не из-за любого `then`. Блокирующий `sync_wait`
в том же единственном потоке, который должен обслужить ожидаемую очередь,
может привести к взаимной блокировке.

Из корня проекта:

./build/additions/execution/06-scheduler-transfer/main

На Windows используйте `scripts/build-windows.sh` через MSYS2 Bash и файл `.exe`.
[Настройка F5/Ctrl+F5](../../../README.md#сборка-и-запуск-в-vs-code).

Успех — `OK reference-example` и код `0`; ошибка проверки — код `1`.

## Типичные ошибки

Не уничтожать run_loop до операции. Не присоединять worker до команды `finish`. Не вызывать блокирующее ожидание на единственном занятом потоке нужного executor.
