# 07. Senders внутри корутины

## Версия C++

C++26 — режим сборки; механизмы и даты их появления указаны в исходниках. Учебный компилятор — GCC 16+.

## Что изучаем

Связываем два способа записи асинхронных шагов. Нужны Task, каналы завершения и профиль stdexec.

## Примеры

- [main.cpp](main.cpp) — самостоятельный пример; успешное завершение — код `0`.

## Как это работает

Этот исходник **целенаправленно использует внешний `stdexec::task`**. Он не
утверждает наличие стандартного `std::task` в C++26. Promise данного типа знает,
как превратить sender в awaiter: `co_await just(21)` даёт число `21`, а `co_return`
возвращает `42`. Задача также пригодна как sender для `stdexec::sync_wait`.

В `failure` исключение возникает внутри `then`, проходит через ошибочный канал,
ожидание корутины и `sync_wait`, затем ловится в `main`. Кадры и состояния операции
сохраняются до завершения; локальная функция не хранит handle в чужой долгоживущей
очереди. Само наличие произвольного sender не делает его ожидаемым в любой корутине:
совместимость обеспечивает promise конкретной библиотеки.

Подготовка: `python3 scripts/prepare-reference-libraries.py`. Соберите общей командой
с `REFERENCE_LIBRARIES=1`. Без внешнего профиля возвращается `77` с явным сообщением,
даже если когда-нибудь появится стандартный execution: этот пример проверяет
конкретный мост stdexec. [Различия профилей](../reference-libraries.md).

## Типичные ошибки

Не переносить `co_await sender` в произвольный собственный Task без адаптации promise. Не называть сторонний `stdexec::task` стандартным типом C++26. Не скрывать пропуск основного сценария успешным пустым main.
