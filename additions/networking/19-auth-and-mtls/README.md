# 19. Аутентификация, права доступа и mTLS

## Версия C++

C++17 — режим сборки; механизмы и даты их появления указаны в исходниках. Учебный компилятор — GCC 16+.

## Что изучаем

Разделяем доказательство личности и разрешение конкретного действия. Нужны HTTPS и HTTP.

## Примеры

- [main.cpp](main.cpp) — настоящий HTTPS-клиент с клиентским сертификатом.
- [main2.cpp](main2.cpp) — локальный HTTP-сервер с проверкой демонстрационного Bearer-токена и роли.

## Как это работает

Обычный HTTPS подтверждает сервер перед клиентом. При mTLS сервер дополнительно
запрашивает клиентский сертификат и проверяет доверенную цепочку.
`CAINFO` задаёт доверие клиенту к серверу; `SSLCERT`/`SSLKEY` — личность клиента.
Проверка цепочки и имени сервера остаётся включённой. Клиентский сертификат
сам по себе не означает право выполнять любые прикладные действия.

Запуск mTLS требует сервера, CA и двух файлов клиента:

```bash
./build/additions/networking/19-auth-and-mtls/main https://localhost:PORT/ ca.pem client.pem client.key
```

Готовая воспроизводимая локальная проверка `python3 additions/networking/tests/check-reference.py`
создаёт временный CA и сертификаты через `openssl`, запускает TLS-сервер на loopback,
проверяет правильного клиента, недоверенного клиента и несовпадение имени сервера.
Файлы помещаются во временный каталог внутри `build`; постоянные сертификаты ОС не меняются.
Без аргументов клиент печатает использование и возвращает `1`; успешный ответ — `mTLS 200`, код `0`.

`main2` обслуживает **четыре** запроса и завершается. Отсутствующий/неверный токен
даёт `401` и `WWW-Authenticate`; известный reader при записи — `403`;
reader при GET и writer при записи — `200`. Токены `demo-reader`/`demo-writer`
заданы в исходнике только для локального учебного сервера. Передача идёт по
незашифрованному HTTP на loopback; это не готовая система выдачи/хранения токенов.
В тесте отправляются эти четыре запроса, затем проверяется завершение сервера.

При обновлении сертификатов нужны новая проверенная цепочка, согласованный ключ,
перезагрузка контекста или процесса и период перекрытия доверия, если меняется CA.
Отзыв, CRL/OCSP и автоматическое обновление в этот клиент не встроены.

## Сборка и запуск

Из корня проекта:

```bash
bash scripts/build-linux.sh additions/networking/19-auth-and-mtls/main.cpp
python3 additions/networking/tests/check-reference.py
```

На Windows используйте `scripts/build-windows.sh` через MSYS2 Bash и файл `.exe`.
[Настройка F5/Ctrl+F5](../../../README.md#сборка-и-запуск-в-vs-code).
Для ручного запуска нужны TLS-сервер и сертификаты; локальная проверка подготавливает их сама.
Успех — `OK reference-example` и код `0`; ошибка проверки — код `1`.

## Типичные ошибки

Не отключать проверку сертификата для исправления доверия. Не считать аутентификацию проверкой роли. Не помещать настоящие токены/ключи в исходники и не выводить ключ в диагностике. mTLS требует поддержки обеих сторон.
