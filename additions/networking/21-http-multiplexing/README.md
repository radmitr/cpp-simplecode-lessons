# 21. Мультиплексирование HTTP и границы QUIC

## Версия C++

C++17 — режим сборки; механизмы и даты их появления указаны в исходниках. Учебный компилятор — GCC 16+.

## Что изучаем

Исполняем две передачи в одном multi handle и читаем фактически согласованный протокол. Нужны HTTP/2–3 и libcurl.

## Примеры

- [main.cpp](main.cpp) — две реальные HTTP-передачи через libcurl multi.
- [Выбор HTTP/1–3](../20-http-versions/main.cpp) — существующий клиент с режимами `h2-only`/`h3-only`.

## Как это работает

Easy handle представляет одну передачу, multi handle обслуживает несколько.
Оба добавлены до цикла `perform`/`poll`; readiness сокетов обрабатывает libcurl,
а `poll` предотвращает активное вращение CPU. После завершения проверяются все
`CURLMSG_DONE`, транспортные ошибки и HTTP-статусы. RAII удаляет easy handles из
multi до их освобождения и освобождает multi последним.

`CURL_HTTP_VERSION_2TLS` запрашивает HTTP/2 для TLS с возможностью согласованного
отката. `PIPEWAIT` даёт шанс дождаться соединения для мультиплексирования,
`MAX_HOST_CONNECTIONS=1` ограничивает число соединений к хосту. Печатается реально
использованная версия и число новых соединений: успешные два запроса **не доказывают**,
что сервер согласовал HTTP/2 или что потоки перекрывались во времени.
Для этого нужно проверить согласованный протокол и трассировку/службу с HTTP/2.

Ручной запуск: `main URL1 URL2 [ca.pem]`. Локальный runner
`python3 additions/networking/tests/check-reference.py` проверяет два ответа на loopback;
это базовая проверка multi на HTTP/1.1. Для TLS можно передать CA без отключения
проверок. Без аргументов — использование и код `1`.

HTTP/2 мультиплексирует логические потоки поверх TCP; потерянные TCP-байты могут
задержать доставку данных разных потоков. HTTP/3 переносит HTTP поверх QUIC/UDP:
отдельные QUIC-потоки устраняют эту конкретную общую очередь доставки, но общие
ограничения перегрузки и потери пакетов остаются. UDP сам по себе не предоставляет
надёжность и шифрование QUIC. Реализацию QUIC этот пример не пишет: она входит
в выбранный backend libcurl. Изучение формата пакетов, миграции соединения и 0-RTT
требует отдельного разбора; 0-RTT также связан с риском повторного выполнения.

## Сборка и запуск

Из корня проекта:

```bash
bash scripts/build-linux.sh additions/networking/21-http-multiplexing/main.cpp
python3 additions/networking/tests/check-reference.py
```

На Windows используйте `scripts/build-windows.sh` через MSYS2 Bash и файл `.exe`.
[Настройка F5/Ctrl+F5](../../../README.md#сборка-и-запуск-в-vs-code).
Внешние службы и интерактивный ввод не нужны, если ниже не оговорено иное.
Успех — `OK reference-example` и код `0`; ошибка проверки — код `1`.

## Типичные ошибки

Не выдавать два одновременных easy handle за подтверждение HTTP/2–3. Не удалять easy handle до удаления из multi. Не путать curl multi с обязательным запуском отдельных потоков.
