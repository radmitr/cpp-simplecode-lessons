# 16. atomic::wait и уведомления — C++20

- main.cpp — один читатель, wait(false) и notify_one().
- main2.cpp — три читателя и notify_all().

ready.wait(false) ожидает, пока значение атомарного ready перестанет быть false.
Это не ожидание произвольного предиката, как у condition_variable.
Если ready уже true к моменту вызова, ждать не нужно.

## Порядок действий

Производитель сначала записывает payload = 42, затем ready.store(true),
затем вызывает notify_one или notify_all.
notify не меняет ready: если только уведомить без изменения значения,
ожидание может продолжиться.

В коде у `store()` и `wait()` не указан порядок памяти. По умолчанию они
используют `seq_cst`. В этом примере он обеспечивает следующее:
после того как `wait(false)` увидит `ready == true`, читатель может безопасно
прочитать записанное перед этим значение `payload`.
Главный поток после установки `ready` больше не меняет `payload`.
В следующем бонусе [memory_order](../17-memory-order/) та же передача данных
разобрана с явными `acquire` и `release`.

У main2.cpp каждый читатель должен вывести 42, итог Completed readers: 3.
Мьютекс там защищает счётчик completed и составные сообщения.
Само уведомление не обеспечивает исключительный доступ к этим данным.

## Ограничения ожидания

В реализации возможны внутренние пробуждения без изменения значения,
но wait возвращается только после наблюдения отличающегося значения.
Если другой поток успеет изменить `ready` с `false` на `true` и обратно
на `false`, ожидающий поток может не заметить промежуточное `true`
и продолжить ждать. Такой пропуск изменения называют проблемой ABA.
В примерах `ready` меняется только один раз: с `false` на `true`.

Обычный atomic::wait не принимает таймаут.
Для ожидания с таймаутом есть condition_variable или другие подходящие примитивы.
Такое ожидание позволяет обойтись без собственного цикла постоянных проверок;
конкретный способ ожидания выбирает реализация библиотеки.
