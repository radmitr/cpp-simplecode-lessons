# 04. `std::condition_variable`

## Версия C++

`std::thread`, `std::mutex`, `std::lock_guard`, `std::unique_lock`, `std::condition_variable` — **C++11**.
`std::string` — **C++98**.

Сборка примеров: **C++17**. Это режим проекта,
а не дата появления всех использованных конструкций.

## Что изучаем

Рабочий поток ждёт, пока `main` подготовит строку. Он не проверяет `ready`
в бесконечном цикле и не подбирает длительность `sleep_for` для ожидания данных.

## Примеры

- [main.cpp](main.cpp) — `wait()` с предикатом и `notify_one()`: один поток ждёт строку.
- [main2.cpp](main2.cpp) — `wait_for()` и `wait_until()` с предикатом: ожидание с таймаутом.
- [main3.cpp](main3.cpp) — `notify_all()`: три потока ожидают одно общее условие.
- [main4.cpp](main4.cpp) — ожидание без предиката, цикл проверки и `std::cv_status`.

Выбирайте один исходник с `main()`; варианты запускаются отдельно.

## Как это работает

### `main.cpp`: ожидание строки с предикатом

~~~cpp
cv.wait(lock, [&]() { return ready; });
~~~

Сокращённый фрагмент; полный пример: [main.cpp](main.cpp).

Лямбда `[&]() { return ready; }` — это условие ожидания, или предикат.
Она возвращает `true`, когда данные готовы.

Для ожидания используется `std::unique_lock`. Вызов `wait()` сначала
проверяет условие под мьютексом. Если оно ложно, `wait()` освобождает мьютекс
и приостанавливает поток. После пробуждения он снова захватывает мьютекс
и проверяет условие. Если `ready` всё ещё равен `false`, ожидание повторяется.
Если `ready` равен `true`, `wait()` заканчивается, оставляя мьютекс захваченным.
Именно поэтому здесь нужен `unique_lock`, у которого есть `lock()` и `unlock()`.

Главный поток под `mutex` записывает `message` и устанавливает `ready = true`.
После освобождения `mutex` он вызывает `notify_one()`. Рабочий поток проверяет `ready`,
копирует строку под `mutex`, освобождает его и печатает полученные данные.

Предикат нужен по двум причинам: возможны ложные пробуждения, а уведомление
может прийти ещё до вызова `wait()`. Состояние `ready` сохраняется, поэтому раннее
уведомление не приведёт к вечному ожиданию. Все обращения к `ready` защищены
одним и тем же `mutex`. Сама `condition_variable` данные не защищает.

Пауза 500 мс изображает подготовку данных. Удалите её — пример останется корректным.

#### Запуск и результат

Для запуска выберите [main.cpp](main.cpp). Аргументы, ввод, файлы и внешние сервисы
не нужны. Ожидаемый вывод:

~~~text
Main: preparing data...
Worker received: Hello from main
Main: worker finished
~~~

Порядок строк фиксирован: первая печатается до установки `ready`,
вторая — после получения строки, третья — после завершения `worker.join()`.
Программа завершается самостоятельно с кодом `0`.

### `main2.cpp`: ожидание с ограничением времени

`wait(lock, predicate)` ждёт, пока условие станет истинным.
`wait_for(lock, duration, predicate)` ограничивает ожидание длительностью,
например 100 миллисекундами.
`wait_until(lock, deadline, predicate)` использует конкретный момент времени.
Для измерения интервалов здесь используется `std::chrono::steady_clock`, не зависящий
от перевода системных часов.

`wait(lock, predicate)` не возвращает значение (`void`): он заканчивается,
когда условие выполнено. Варианты `wait_for` и `wait_until` с предикатом
возвращают `bool`: `true` — условие выполнено при последней проверке;
`false` — время ожидания истекло, а условие всё ещё ложно.
Без предиката эти два метода возвращают `cv_status`, а обычный `wait` — `void`.
Само пробуждение без проверки условия не доказывает готовность данных.

В `main2.cpp` первое ожидание гарантированно видит `ready == false`:
производитель ещё не создан, поэтому `wait_for` заканчивается по таймауту.
Затем запускается производитель и `main` ждёт через `wait_until`.
Обычно второе ожидание получает `ready`; при задержке планирования возможен таймаут.
По завершении ожидания `producer.join()` всё равно дожидается производителя.

Каждая пара фигурных скобок вокруг `std::unique_lock<std::mutex> lock(mtx)`
задаёт отдельную область видимости: `lock` существует до конца этого блока.
После нормального возврата из `wait_for()` или `wait_until()` мьютекс `mtx`
снова захвачен, в том числе при таймауте, и остаётся захваченным во время вывода.
При выходе из блока деструктор `lock` автоматически освобождает `mtx`.

В первом блоке это происходит до создания `producer`, во втором — до
`producer.join()`. Если второе ожидание завершилось по таймауту и `ready`
ещё равен `false`, производителю может понадобиться `mtx`, чтобы установить
`ready = true` и завершиться. Если вызвать `join()`, продолжая удерживать `mtx`,
возникнет взаимная блокировка: главный поток будет ждать завершения производителя,
а производитель — освобождения мьютекса главным потоком.

Таймаут не даёт жёсткой гарантии времени возврата:
для продолжения потоку нужно снова получить `mutex` и процессорное время.

#### Запуск и результат

Для запуска выберите [main2.cpp](main2.cpp). Аргументы, ввод, файлы и внешние сервисы
не нужны. Обычный вывод:

~~~text
wait_for: timeout
wait_until: ready
~~~

Первая строка всегда `wait_for: timeout`. Во второй допустимо
`wait_until: timeout`, если при последней проверке условие ещё не выполнено
после истечения срока ожидания. Порядок строк фиксирован.
После `producer.join()` программа завершается самостоятельно с кодом `0`,
в том числе при таймауте второго ожидания.

### `main3.cpp`: уведомление всех ожидающих

Метода `notify()` у `std::condition_variable` нет:

- `notify_one()` пробуждает одного из ожидающих.
- `notify_all()` пробуждает всех ожидающих.

Уведомление не передаёт данные и не меняет `ready`. Сначала измените защищённое
состояние, затем уведомите ожидающих. В примерах уведомление вызывается
после освобождения `mutex`. Разбуженным потокам всё равно нужно захватить его,
поэтому в `main3.cpp` они печатают по очереди. Порядок номеров неизвестен.

Слово «пробуждает» не означает, что все потоки сразу одновременно выполняют
следующую строку. После `notify_all()` все они перестают ждать на
`condition_variable` и пытаются снова захватить один и тот же `mutex`. Один поток
получает `mutex`, а остальные временно ждут его освобождения. Они уже не ждут на
`condition_variable`, поэтому ещё один вызов `notify_all()` им не нужен:

~~~text
notify_all()
    ↓
все потоки перестают ждать на condition_variable
    ↓
все пытаются захватить mutex
    ↓
один поток получает mutex, остальные ждут mutex
~~~

Если после проверки общего состояния освободить `mutex` через `lock.unlock()`,
потоки смогут выполнять дальнейшую независимую работу параллельно. В `main3.cpp`
`mutex` удерживается во время вывода, поэтому сообщения печатаются по одному.

Если бы `main3.cpp` уведомил только одного уже ожидающего через `notify_one()`,
остальные могли бы остаться ждать. Те, кто пришёл после установки `ready`,
пройдут сразу благодаря предикату. Ранние уведомления сами по себе не сохраняются:
сохраняется состояние `ready` под `mutex`.

#### Запуск и результат

Для запуска выберите [main3.cpp](main3.cpp). Аргументы, ввод, файлы и внешние сервисы
не нужны. Один из допустимых вариантов вывода:

~~~text
Worker 1: ready
Worker 2: ready
Worker 3: ready
~~~

Каждый работник с номером `1`, `2` и `3` печатает ровно одну строку.
Допустима любая перестановка этих трёх строк; части разных сообщений
не перемешиваются, поскольку вывод защищён общим `mutex`.
Порядок вызовов `t1.join()`, `t2.join()` и `t3.join()` не задаёт порядок вывода:
они только дожидаются завершения соответствующих потоков.
После всех трёх `join()` программа завершается самостоятельно с кодом `0`.

### `main4.cpp`: вариант без предиката

Обычный `cv.wait(lock)` возвращает `void` и может проснуться без изменения данных.
Поэтому он находится внутри `while (!ready)`. Проверка выполняется
с захваченным `mtx`; ложное пробуждение приводит к следующему ожиданию.
Перегрузка с предикатом делает такой цикл внутри библиотечной функции.

`wait_for(lock, duration)` и `wait_until(lock, deadline)` без предиката
возвращают `std::cv_status`: `timeout` или `no_timeout`.
`no_timeout` не доказывает готовность данных: нужна отдельная проверка.
В начале программы `wait_for()` получает нулевую длительность,
а `wait_until()` — текущий момент `std::chrono::steady_clock::now()`.
При проверке срок ожидания уже истёк, поэтому оба вызова возвращают `timeout`.
Получение `no_timeout` этот пример не демонстрирует.
Корректность последующей передачи `42` от этих двух вызовов не зависит.

Главный держит `mtx` при создании производителя. Производитель получает
его после освобождения мьютекса ожиданием, записывает число и `ready`,
затем уведомляет. Главный копирует число под мьютексом и освобождает его
до `join()`.

#### Запуск и результат

Для запуска выберите [main4.cpp](main4.cpp). Аргументы, ввод, файлы и внешние сервисы
не нужны. Ожидаемый вывод:

~~~text
wait_for: timeout
wait_until: timeout
Received: 42
~~~

Порядок строк фиксирован. Программа завершается самостоятельно с кодом `0`,
если получено `42`; код `1` предусмотрен для ошибки проверки результата.
В текущем корректном примере ожидается код `0`.
