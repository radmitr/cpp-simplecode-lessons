# 11. Учебный пул потоков

Продолжение [producer–consumer](../10-producer-consumer/), C++17.
Три постоянных рабочих потока выполняют семь заданий из общей очереди.
Новый поток для каждого задания не создаётся.

- main.cpp — использование пула и получение результатов.
- main2.cpp — отмена ожидающих заданий через cancelPending().
- ThreadPool.hpp — класс ThreadPool; подключается через include.
  Отдельно запускать заголовочный файл не нужно.

## Как устроен пул

Конструктор создаёт рабочие потоки. Каждый выполняет цикл `work()`:

1. Ждёт появления задачи или сигнала завершения `stopping`.
2. Под мьютексом извлекает из очереди одну задачу.
3. Освобождает мьютекс и выполняет задачу, затем возвращается к ожиданию.

Если установлен `stopping`, работник сначала разбирает оставшиеся задачи.
Он завершается, когда одновременно выполнены два условия:
`stopping == true` и очередь пуста.

submit() принимает функцию без аргументов, возвращающую int.
Это намеренное ограничение учебного класса. Аргументы можно захватить лямбдой.
Для функции создаётся `packaged_task<int()>` — объект, который вызывает
функцию и сохраняет её результат или исключение. Метод `submit()` возвращает
связанный `future<int>`; через него вызывающий код получает этот результат.

Сам `packaged_task` нельзя копировать, а `std::function<void()>` в нашей
очереди требует, чтобы сохранённую функцию или лямбду можно было скопировать.
Поэтому лямбда хранит `shared_ptr` на `packaged_task`: этот указатель копируется
и сохраняет задачу в памяти, пока она ожидает или выполняется.

## Что показывает main

Шесть задач возвращают квадраты чисел 1–6. Седьмая выбрасывает runtime_error.
Результаты читаются в порядке добавления: 1, 4, 9, 16, 25, 36.
Это не означает, что задачи завершились именно в таком порядке.
Их сумма равна 91. Исключение извлекается через failed.get(),
при этом рабочий поток продолжает обрабатывать другие задания.

При выходе из блока деструктор пула устанавливает stopping,
будит работников и делает join() для каждого. Работники сначала
обрабатывают всю очередь и только затем завершаются.
Результаты хранятся отдельно от самого пула. Если у полученного `future`
ещё не вызывали `get()`, результат можно извлечь и после уничтожения пула.

## Ограничения примера

Нулевой размер пула отклоняется. Если создание одного потока не удалось,
конструктор завершает уже созданные потоки и повторно выбрасывает исключение.

Деструктор ожидает окончания задач и не прерывает их принудительно.
Владелец должен обеспечить, чтобы пул существовал на протяжении обращений к нему.
Нельзя уничтожать пул из его же задания.
Если все работники заняты задачами, которые ждут результатов других задач
из очереди этого же пула, свободных работников для выполнения очереди
не останется. Все будут ждать друг друга — получится взаимная блокировка.
Приоритеты, принудительная остановка выполняющихся задач и ограничение очереди не реализованы.

Откройте main.cpp и нажмите F5 или Ctrl+F5.

## main2.cpp — отмена заданий, которые ещё в очереди

`cancelPending()` убирает из очереди задачи, которые работники ещё не забрали.
Метод возвращает количество убранных задач. Внутри он действует так:

1. Захватывает мьютекс и обменивает очередь пула с пустой локальной очередью.
2. Освобождает мьютекс. Очередь пула теперь пуста, работники могут продолжать работу.
3. Перед возвратом из метода уничтожается локальная очередь и хранившиеся в ней
   ещё не запущенные `packaged_task`.

У этих задач уже есть `future`, но предоставить результат больше некому.
Поэтому вызов `get()` у такого `future` выбрасывает `std::future_error`
с кодом `future_errc::broken_promise`. В этом примере так сообщается об отмене;
в общем случае эта ошибка означает, что задача осталась без результата.

Задание, уже извлечённое работником из очереди, отмена не затрагивает.
В конкурентном коде результат cancelPending() зависит от того,
что работники успели забрать до захвата мьютекса отмены.
После `cancelPending()` можно снова вызывать `submit()`: метод не закрывает пул.

Чтобы при каждом запуске отменялись именно две задачи, `main2.cpp` создаёт
одного работника. Первое задание через `started.set_value()` сообщает,
что начало выполняться, и ждёт разрешения продолжить через `gate.wait()`.

Главный поток дожидается этого сообщения, добавляет ещё два задания и вызывает
`cancelPending()`. Единственный работник всё ещё занят первой задачей,
поэтому эти два задания остаются в очереди и оба отменяются.

Затем главный поток вызывает `release.set_value()`, разрешая первой задаче
продолжить. Она возвращает 42. От двух отменённых задач главный поток получает
ошибки `broken_promise`, а от новой задачи, добавленной после отмены, — число 7.

Порядок этих действий обеспечивают `promise` и `future`, поэтому подбирать
длительность `sleep_for` не нужно. `cancelPending()` не прерывает уже работающие
задачи. Для их остановки сама задача должна проверять запрос на завершение,
например через `stop_token`.

Ожидается Cancelled queued tasks: 2, Running task result: 42,
две строки Queued task cancelled: broken_promise и Next task result: 7.
Исходный main.cpp по-прежнему демонстрирует обработку всей очереди при уничтожении пула.
