# 08. `std::shared_mutex` и `std::shared_lock`

## Версия C++

`std::shared_mutex` — **C++17**.
`std::shared_lock` — **C++14**.
`std::thread`, `std::mutex`, `std::lock_guard`, `std::unique_lock`, `std::chrono` — **C++11**.

Сборка примеров: **C++17**. Это режим проекта,
а не дата появления всех использованных конструкций.

## Что изучаем

Пример использует C++17. Три потока читают общую настройку,
один поток меняет её с 0 на 42.

## Примеры

- [main.cpp](main.cpp).

Выбирайте один исходник с `main()`; варианты запускаются отдельно.

- [main2.cpp](main2.cpp): другой писатель меняет значение между совместным и исключительным захватами.

## Как это работает

### Два режима доступа

`std::shared_lock<std::shared_mutex>` используется читателями.
Несколько потоков могут одновременно читать `setting`, удерживая
один и тот же `settingsMutex` в этом режиме. В примере каждый читатель
ждёт 100 мс, не освобождая свой `shared_lock`, чтобы показать их совместную работу.

`std::unique_lock<std::shared_mutex>` используется писателем.
Он ждёт освобождения мьютекса всеми читателями. Когда захват получен,
писатель меняет `setting`, а новые читатели и другие писатели ждут.
В этом примере мьютекс освобождается при уничтожении объекта `lock`
в конце функции писателя.

shared_lock не делает запись безопасной: читатели не должны менять
общие данные под совместным захватом. Для изменения нужен исключительный режим.

### Что будет в консоли

Каждый читатель печатает начало и конец чтения. `snapshot` — локальная копия
`setting`, полученная под shared_lock. Отдельный `outputMutex` защищает вывод:
совместное владение `settingsMutex` не исключает одновременную печать читателей.

Номера читателей и момент запуска писателя заранее неизвестны.
Читатель может увидеть 0 или 42; после всех `join()` итог всегда Final `value`: 42.
Пауза не задаёт порядок потоков. `shared_mutex` также не обещает конкретной
очередности обслуживания читателей и писателей.

[Все бонусы и команды сборки](../README.md).
[Описание совместного владения](https://eel.is/c++draft/thread.sharedmutex.requirements).

### Общие данные и переход между режимами

shared_lock разрешает совместное владение, но не делает каждый доступ
под ним чтением автоматически. Код всё ещё обязан не изменять общую `setting`.
Локальный `snapshot` можно затем использовать независимо, если его получили
при корректно удерживаемом захвате и больше не обращаются к изменяемой `setting`.

Стандартный `shared_mutex` не предоставляет атомарного upgrade:
отпустить shared_lock и взять `unique_lock` — два действия, между которыми
другой писатель может изменить данные. После перехода условие надо проверить снова.

Нельзя повторно захватывать этот же `shared_mutex` тем же потоком как
`recursive_mutex`. Необходимость отдельного `outputMutex` объясняется просто:
три разрешённых читателя могут одновременно печатать свои сообщения.

### `main2.cpp`: почему после смены режима проверяют условие заново

В программе значение сначала равно `10`. Главный поток берёт
`shared_lock` и сохраняет `snapshot = 10`. Чтобы менять данные,
он должен отпустить совместный захват и взять `unique_lock`.
Эти действия не образуют одной атомарной операции.

1. `reader.unlock()` освобождает совместный захват.
2. Сигнал `gapOpened` разрешает другому писателю выполнить работу.
3. Писатель под исключительным захватом устанавливает `20` и сообщает о завершении.
4. Главный берёт исключительный захват и сравнивает текущее значение со снимком.
5. Значения различаются, поэтому решение «увеличить прежнее значение» отменяется.

Сигналы `promise/future` гарантируют нужный промежуток; задержки планировщика
не используются как доказательство порядка. Число остаётся `20`.
Вывод: `Snapshot: 10; final: 20; updated from old snapshot: false`.
Сам `shared_mutex` не предоставляет атомарного upgrade.
Подробнее о сигналах — [promise и future](../09-promise-future/README.md).

Для запуска выберите `main2.cpp` либо замените `main` на `main2`
в [общих командах](../../../README.md#сборка-из-терминала).
Ввода и файлов нет, успех — `0`, неверный результат — `1`.
