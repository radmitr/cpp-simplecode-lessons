# 02. std::mutex::try_lock


Откройте main.cpp и нажмите F5 или Ctrl+F5 в VS Code.

Сначала главный поток удерживает mtx, а рабочий вызывает mtx.try_lock().
Захват не удаётся: try_lock возвращает false без ожидания освобождения mtx.
Рабочий поток пропускает работу и завершается, поэтому main может дождаться
его через join(), а затем освободить мьютекс. Паузы sleep_for для этого не нужны.

После освобождения mtx главный поток снова вызывает tryIncrement().
Обычно эта попытка успешна, счётчик увеличивается до 1. Возможный вывод:

~~~text
Main: holding the mutex
try_lock: not acquired; skipping work
Main: mutex released; trying again
try_lock: acquired; counter = 1
Final counter: 1
~~~

Разница с lock(): lock() ждёт возможности захвата, а try_lock() сообщает
результат одной попытки. Если заменить try_lock на блокирующий захват
в рабочем потоке этого примера, получится deadlock: main удерживает mtx
и ждёт worker, а worker ждёт освобождения mtx главным потоком.
Обычно join() вызывают за пределами области удержания мьютекса;
здесь ожидание внутри блока допустимо именно потому, что worker не ждёт mtx.

При результате true мьютекс принадлежит вызывающему потоку.
std::lock_guard с std::adopt_lock принимает уже захваченный мьютекс
и освобождает его в конце блока. Без adopt_lock guard попытался бы
повторно захватить обычный mutex, что является ошибкой.
При false нельзя менять защищённые данные или вызывать unlock().

Стандарт допускает ложную неудачу try_lock даже для свободного мьютекса.
Поэтому false означает «захват не получен», а не доказательство занятости.
Пример обрабатывает обе ветки и после второй попытки может вывести 0.
try_lock полезен, когда при неудаче можно пропустить действие или выполнить
другую работу; постоянные попытки в пустом цикле могут напрасно расходовать CPU.

[Требования к try_lock в проекте стандарта](https://eel.is/c++draft/thread.mutex.requirements.mutex).


## Зачем здесь adopt_lock

Обычный guard сам захватывает мьютекс:

~~~cpp
std::lock_guard<std::mutex> guard(mtx); // вызывает mtx.lock()
~~~

Но после успешного try_lock() мьютекс уже захвачен текущим потоком:

~~~cpp
if (mtx.try_lock())
{
    std::lock_guard<std::mutex> guard(mtx, std::adopt_lock);
    ++counter;
} // guard вызывает mtx.unlock()
~~~

std::adopt_lock — специальная метка для конструктора, а не команда захвата.
Она сообщает: «этим мьютексом уже владеет текущий поток».
Конструктор сохраняет ссылку, не вызывает lock() повторно,
а деструктор по-прежнему вызывает unlock().
Нельзя передавать adopt_lock, если текущий поток не захватил мьютекс:
это нарушение требований конструктора и неопределённое поведение.

Управление мьютексом зависит от способа создания объекта:

- lock_guard(mtx) — захватить сейчас и освободить в конце блока.
- lock_guard(mtx, std::adopt_lock) — принять уже захваченный мьютекс и освободить в конце блока.
- unique_lock(mtx, std::defer_lock) — пока не захватывать; позднее можно вызвать lock().

Если создавать отдельный урок о метках блокировки, в нём стоит сравнить
adopt_lock, defer_lock и try_to_lock. Здесь adopt_lock разобран рядом с местом использования.

[Требования к lock_guard с adopt_lock](https://eel.is/c++draft/thread.lock.guard).
