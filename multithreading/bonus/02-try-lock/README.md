# 02. std::mutex::try_lock

`try_lock()` позволяет попытаться захватить мьютекс, не ожидая его освобождения.
В примере поток увеличивает `counter`, только если захват удался.
При неудаче он пропускает увеличение и завершает работу.

Откройте `main.cpp` и нажмите F5 или Ctrl+F5 в VS Code.

## Чем try_lock отличается от lock

Если мьютекс занят другим потоком:

| Вызов | Что делает поток |
|---|---|
| `mtx.lock()` | Ждёт освобождения `mtx`, затем захватывает его и продолжает работу. |
| `mtx.try_lock()` | Возвращает `false` без ожидания освобождения `mtx`. Дальнейшие действия определяет ваш код. |

Если `try_lock()` вернул `true`, текущий поток захватил мьютекс.
Теперь можно обращаться к защищённым данным, а после работы нужно освободить
мьютекс. В этом примере освобождение поручено `std::lock_guard`.

## Что происходит в main.cpp

1. Главный поток создаёт `guard`, который захватывает `mtx`.
2. Главный поток запускает рабочий поток `worker`.
3. Рабочий поток вызывает `tryIncrement()`. Его попытка `mtx.try_lock()`
   возвращает `false`: мьютекс всё ещё удерживает главный поток.
4. Рабочий поток печатает сообщение о неудаче и завершается, не меняя `counter`.
5. Вызов `worker.join()` в главном потоке заканчивается. Затем главный поток
   выходит из блока: объект `guard` уничтожается и освобождает `mtx`.
6. Главный поток сам вызывает `tryIncrement()`. Теперь мьютекс свободен;
   при успешной попытке `counter` увеличивается с 0 до 1.

Один из возможных вариантов вывода:

~~~text
Main: holding the mutex
try_lock: not acquired; skipping work
Main: mutex released; trying again
try_lock: acquired; counter = 1
Final counter: 1
~~~

Стандарт разрешает `try_lock()` вернуть `false` даже для свободного мьютекса.
Поэтому вторая попытка тоже может не удаться, и итоговый счётчик останется 0.
Результат `false` означает только «этот поток не захватил мьютекс».

## Почему здесь join не приводит к зависанию

`worker.join()` ждёт завершения рабочего потока. Во время этого ожидания
главный поток продолжает удерживать `mtx`.

С `try_lock()` рабочий поток не ждёт `mtx`: при неудаче он сразу пропускает
увеличение счётчика и завершается. Поэтому `join()` может закончиться.

Если рабочий поток вместо этого будет ждать мьютекс через `lock()`,
возникнет взаимная блокировка — deadlock:

1. Главный поток ждёт завершения рабочего потока в `join()`.
2. Рабочий поток ждёт, когда главный освободит `mtx`.
3. Главный поток освободит `mtx` только после выхода из `join()` и блока.

Ни один из них не сможет продолжить. Если рабочему потоку нужен блокирующий
захват, главный поток должен освободить нужный ему мьютекс до вызова `join()`.

## Зачем нужен adopt_lock

Обычный `std::lock_guard<std::mutex> guard(mtx)` вызывает `mtx.lock()`
при создании и `mtx.unlock()` при уничтожении.

Внутри ветки успешного `try_lock()` мьютекс уже захвачен. Здесь нужен другой
конструктор `lock_guard` — с меткой `std::adopt_lock`:

~~~cpp
if (mtx.try_lock()) // При true текущий поток уже захватил mtx.
{
    std::lock_guard<std::mutex> guard(mtx, std::adopt_lock);
    ++counter;
} // guard уничтожается и вызывает mtx.unlock().
~~~

С этой меткой объект `guard` не вызывает `lock()` при создании.
Он берёт на себя освобождение уже захваченного мьютекса в конце блока,
в том числе при выходе из блока из-за исключения.

Если убрать `std::adopt_lock`, конструктор попытается повторно захватить
`std::mutex`, которым этот же поток уже владеет. Это неопределённое поведение;
в частности, программа может зависнуть.

При `false` поток не владеет `mtx`. Поэтому в ветке `else` нельзя создавать
такой `guard` с `adopt_lock`, вызывать `mtx.unlock()` или менять защищённый
счётчик. В нашем коде эта ветка только печатает сообщение.

`try_lock()` подходит, когда при неудаче можно пропустить действие или заняться
другой работой. Пустой цикл, который постоянно повторяет попытку, расходует
процессорное время на проверки.
