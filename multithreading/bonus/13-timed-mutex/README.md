# 13. std::timed_mutex

C++17. Продолжение [try_lock](../02-try-lock/).
try_lock делает попытку без ожидания. timed_mutex позволяет ограничить ожидание:

- try_lock_for(duration) — задать длительность.
- try_lock_until(deadline) — задать момент времени.

В примере объект `std::unique_lock<std::timed_mutex>` создаётся с
`std::defer_lock`: он запоминает мьютекс, но пока не захватывает его.
Затем код вызывает `lock.try_lock_for(...)` или `lock.try_lock_until(...)`.
Результат `true` означает, что мьютекс захвачен; `false` — что захват не удался.
При уничтожении объект `lock` освободит мьютекс, если всё ещё владеет им.

## Почему первые две попытки неудачны

1. Главный поток захватывает `mtx`, запускает `worker` и вызывает `worker.join()`.
2. Рабочий поток делает две попытки захвата, каждой отводится 50 мс.
   Обе возвращают `false`: всё это время `mtx` удерживает главный поток.
3. Рабочий поток завершается, и главный поток выходит из `join()`.
   После выхода из блока объект `owner` освобождает `mtx`.

Если рабочий поток будет использовать обычный `lock()`, он останется ждать
освобождения мьютекса. Главный поток в это время будет ждать завершения
рабочего в `join()`. Освободить мьютекс он сможет только после `join()` —
получится взаимная блокировка, как в [примере с try_lock](../02-try-lock/).

После освобождения `mtx` главный поток делает третью попытку через `try_lock_for()`.
Она обычно успешна. Стандарт допускает ложную неудачу и при свободном мьютексе,
поэтому false означает отсутствие захвата, а не доказательство занятости.
В коде обработаны оба результата.

steady_clock не зависит от перевода системных часов.
Таймаут не является жёстким ограничением времени исполнения:
планирование ОС может задержать возврат.
