# 06. `std::jthread` и `std::stop_token` — C++20

Этот пример собирается как C++20: `cxx-standard.txt` в этой папке содержит `c++20`.
Общие скрипты Windows и Linux читают этот файл автоматически.
При ручной сборке укажите `-std=c++20` `-pthread`.
Если `std::jthread` недоступен, проверьте поддержку C++20 компилятором и библиотекой.

В этом примере `std::jthread` запускает лямбду, принимающую `std::stop_token`.
Через этот объект рабочий поток узнаёт о запросе остановки:
на каждой итерации он проверяет `stop.stop_requested()`.

`std::stop_token` хранит доступ к признаку «поступил запрос остановки».
Он не выполняет работу и не останавливает поток самостоятельно.
В [main.cpp](main.cpp) события идут так: `main` создаёт `worker`, рабочий
поток входит в цикл, а главный продолжает выполнение после конструктора.
Эти два потока выполняются независимо до ожидания при выходе из блока.

Через 350 мс `main` вызывает `worker.request_stop()`. Это только запрос:
он не прерывает `sleep_for` и не останавливает функцию принудительно.
Рабочий поток завершает текущую итерацию и выходит при следующей проверке.

При выходе из внутреннего блока объект `worker` уничтожается.
В нашем коде его деструктор сам вызывает `request_stop()`, а затем `join()`.
Главный поток ждёт завершения рабочего и только после этого продолжает
выполнение за закрывающей скобкой блока. Поэтому явного `join()` в коде нет.

Рабочий поток увеличивает `completed`, а главный читает эту переменную
только после завершения рабочего. Одновременного чтения и записи здесь нет.

Число завершённых итераций зависит от планирования потоков, обычно получается
около четырёх. Не используйте это число как точный результат проверки.

Попробуйте убрать явный `request_stop()`: запрос при выходе из блока выполнит деструктор.
Если функция не проверяет запрос остановки и работает бесконечно, деструктор
будет ждать бесконечно — автоматический `join` не означает принудительное завершение.

## Что автоматизировано, а что остаётся у функции

По сравнению со `std::thread`, `jthread` связывает окончание своей области
с запросом остановки и ожиданием joinable-потока.
Однако условие выхода определяет сама рабочая функция.

~~~cpp
while (!stop.stop_requested()) {
    // Одна ограниченная порция работы.
}
~~~

Сокращённый фрагмент; полный пример: [main.cpp](main.cpp).

Если запрос пришёл во время `sleep_for`, текущая пауза закончится обычным образом.
Поэтому `completed` может включать итерацию, начатую до `request_stop`.
Это не гонка: `main` читает `completed` только после автоматического `join`.

`stop_token` не является владеющим указателем на поток и не вызывает `join`.
Повторные запросы остановки не означают несколько прерываний.
Для ожидания `condition_variable` с реакцией на остановку есть бонус 23.
Не уничтожайте `jthread` под мьютексом, который нужен его функции для завершения:
автоматическое ожидание тоже участвует в зависимостях блокировок.

## Сборка и запуск

Нужны заголовки `<thread>`, `<stop_token>`, `<chrono>` и `<iostream>`.
Откройте [main.cpp](main.cpp): **F5** запускает с отладчиком,
**Ctrl+F5** — без отладчика. Из корня проекта, Linux:

~~~bash
bash scripts/build-linux.sh multithreading/bonus/06-jthread-stop-token/main.cpp
./build/multithreading/bonus/06-jthread-stop-token/main
~~~

Windows, PowerShell:

~~~powershell
& C:\msys64\usr\bin\bash.exe scripts/build-windows.sh multithreading/bonus/06-jthread-stop-token/main.cpp
& .\build\multithreading\bonus\06-jthread-stop-token\main.exe
~~~

Ввод не требуется. Ожидается строка `Worker stopped; completed iterations: N`,
где число `N` зависит от планирования потоков; обычный код завершения — `0`.
