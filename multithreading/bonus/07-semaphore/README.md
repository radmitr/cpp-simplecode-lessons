# 07. Семафор: `std::counting_semaphore`

## Версия C++

`std::counting_semaphore` и `std::binary_semaphore` появились в **C++20**.
Сборка урока: **C++20**, задан через `cxx-standard.txt`.
`std::thread`, мьютексы, лямбды и `emplace_back` — C++11;
`std::vector`, `reserve`, `std::max` и `std::boolalpha` — C++98.

## Что изучаем

Семафор хранит **число разрешений**. Успешный `acquire()` забирает одно,
`release()` добавляет одно. Если разрешений нет, `acquire()` ждёт.
В примере это парковка: машин пять, свободных мест изначально два.
Мьютекс пропускает в защищённый участок одного владельца, а семафор
позволяет задать другое число одновременно допущенных задач.

Нужны [потоки](../../lesson-01-thread/README.md),
[мьютекс и `lock_guard`](../../lesson-07-lock-guard/README.md)
и [`vector`](../../../stl/lesson-01-stl-vector/README.md).

## Примеры

- [main.cpp](main.cpp): парковка, проверка `try_acquire()`, общие счётчики.
- [main2.cpp](main2.cpp): начальное значение `0`, сигнал от другого потока,
  фактический поддерживаемый `max()`.
- [main3.cpp](main3.cpp): `vector<jthread>` и автоматическое ожидание в блоке.
- [main4.cpp](main4.cpp): `try_acquire_for()` и `try_acquire_until()`.

Ввода и файлов нет. При успехе код завершения `0`; при провале встроенной
проверки — `1`. Порядок сообщений машин не фиксирован.

- [main5.cpp](main5.cpp): успешный `try_acquire()` уже расходует разрешение.

## Как это работает

### Почему две двойки

Фрагмент из [main.cpp](main.cpp): `std::counting_semaphore<2> slots(2);`

- `<2>` — требование к типу: поддерживать максимальное значение счётчика
  **не меньше двух**. Это не обязательно точный верхний предел.
- `(2)` — значение при создании конкретного объекта: сейчас доступны два разрешения.

Максимум реализации узнаём через `std::counting_semaphore<2>::max()`,
что показано в `main2.cpp`. Он зависит от стандартной библиотеки и может
быть значительно больше двух. Начальное значение должно лежать от `0`
до `max()`. Для `release(n)` нужно, чтобы `n >= 0` и счётчик после добавления
не превышал `max()`. Нарушение этих требований — ошибка программы,
которую библиотека не обязана превращать в исключение.

Ограничение парковки в два места получается так: начинаем с двух,
каждый въезд забирает одно, каждый выезд возвращает ровно одно.
Сам параметр `<2>` не исправит лишние `release()` в программе.
`std::binary_semaphore` — псевдоним `counting_semaphore<1>`; его используют
как сигнал с логическими состояниями «разрешения нет/есть», соблюдая этот протокол.

### Первая проверка и `boolalpha`

Главный поток дважды вызывает `acquire()` и забирает оба разрешения.
`try_acquire()` не ждёт и возвращает `false`: забирать уже нечего.
`slots.release(2)` возвращает **эти два** разрешения перед запуском машин.

`std::boolalpha` настраивает `std::cout` печатать `bool` как `true/false`
вместо `1/0`. Настройка сохраняется для следующих выводов в этот же поток;
`std::noboolalpha` переключает обратно. На печать обычных `int` она не влияет.

У `try_acquire()` возможна и ложная неудача при наличии разрешения:
`false` говорит только «эта попытка не забрала разрешение».
`acquire()` продолжает пытаться до успеха.
В `main4.cpp` обе попытки с таймаутом возвращают `false`, потому что никто
не добавляет разрешений. `for` задаёт длительность, `until` — момент времени;
планировщик может задержать фактический возврат. Успех возвращает `true`
и **уже забирает** разрешение: второй `acquire()` после успеха не нужен.

### Где создаются потоки

`cars` имеет тип `std::vector<std::thread>`.
`cars.reserve(5)` выделяет память минимум для пяти элементов, но
`cars.size()` остаётся `0`. Ни элементов, ни потоков эта строка не создаёт.

`cars.emplace_back([&, id]() { ... });` конструирует новый элемент
`std::thread` непосредственно в конце вектора. Аргумент его конструктора —
лямбда. Поэтому **именно здесь запускается очередной поток**;
после строки размер вектора увеличивается на один.

В `[&, id]` используемые внешние объекты (`slots`, `mtx`, счётчики)
захватываются по ссылке, а `id` — отдельной копией для этой машины.
Иначе все работники могли бы читать меняющуюся переменную цикла,
которая позже вообще перестаёт существовать. Общие объекты живут
до завершения всех `join()`.

### Путь одной машины

1. `slots.acquire()` ждёт место, если нужно, затем забирает разрешение.
2. `guard(mtx)` получает мьютекс для короткого изменения счётчиков и печати.
3. `++parked` регистрирует въезд; `peak = std::max(peak, parked)` сохраняет
   наибольшее замеченное значение.
4. На `}` уничтожается `guard`, мьютекс освобождается.
5. Сон 100 мс изображает стоянку. Разрешение семафора ещё занято,
   но мьютекс **этот работник не удерживает**.
6. Второй `guard` защищает `--parked`, `++completed` и сообщение о выезде.
7. После освобождения мьютекса `slots.release()` возвращает разрешение.

Да, после `acquire()` и перед захватом `mtx` другой поток может успеть
выполниться. Это нормально: семафор допускает две машины, мьютекс
сериализует только учёт и печать. Мгновенно счётчик `parked` может отставать
от количества уже взятых разрешений, пока машина ещё не записала свой въезд.
Порядок по `id` и справедливое обслуживание очереди не гарантируются.

Сон находится **после успешного `acquire()`**. Ожидающий места работник
до сна ещё не дошёл. Ни при таком ожидании, ни при сне он сам не держит
`mtx`; в это время другой работник может кратковременно держать его.

### `parked`, `peak` и `completed`

`parked` — сколько въездов сейчас зарегистрировано без соответствующего выезда.
`peak` — максимум этого числа за всё время, `completed` — количество выездов.
Например: два въезда дают `parked=2, peak=2, completed=0`.
После одного выезда: `parked=1, peak=2, completed=1`.
Они не обязаны совпадать.

`std::max(peak, parked)` возвращает большее число. Именно присваивание
`peak = ...` изменяет `peak`. Начальный `release(2)` управляет разрешениями,
а не историей счётчика, поэтому не заменяет вычисление максимума.
В конце: `completed == 5`, `parked == 0`, `peak <= 2`.
Пик часто равен двум, но расписание может дать один.

`release()` находится вне блока мьютекса, потому что счётчики уже обновлены,
а методы семафора сами поддерживают безопасные параллельные вызовы.
Разместить его внутри блока **после** обновления счётчиков тоже допустимо,
но ожидающая машина тогда может проснуться и сразу ждать ещё и мьютекс.
Важно вернуть разрешение после окончания работы с занимаемым ресурсом.

### Почему другой поток может делать `release`

Мьютекс должен отпустить поток, который его захватил.
Семафор не запоминает владельца разрешения.

В [main2.cpp](main2.cpp) `ready(0)` не пропускает получателя.
Главный записывает `payload=42` и делает `ready.release()`,
хотя сам не вызывал `acquire()`. Получатель проходит `acquire()`
и безопасно читает `42`: передача разрешения также обеспечивает
видимость предшествующей записи. Сигнал не теряется, если получатель
ещё не успел начать ожидание. Одно разрешение расходуется один раз.

### Зачем цикл `join()`

В `main.cpp` хранятся обычные `std::thread`. Нужно дождаться **каждого**
до чтения итогов и уничтожения вектора. Иначе чтение может попасть
на одновременную запись, а уничтожение `joinable`-объекта `thread`
вызовет `std::terminate()`.

В [main3.cpp](main3.cpp) вектор содержит `std::jthread` и помещён
во **внутренний блок**. Деструкторы элементов ждут задачи при выходе
из блока, и лишь затем печатается итог `Completed after automatic joins: 5`.
Просто заменить тип и оставить печать до уничтожения вектора недостаточно.

Метод семафора `acquire()` и атомарный порядок `std::memory_order_acquire`
— разные API с родственным смыслом синхронизации.
Здесь не нужно выбирать порядок памяти аргументом.
Самостоятельный разбор с кодом:
[Порядки памяти: `relaxed`, `release` и `acquire`](../17-memory-order/README.md).

### `main5.cpp`: успешная попытка тоже захватывает

Создаём `binary_semaphore permit(1)`. `try_acquire()` пробует забрать
разрешение без ожидания. Ложный `false` допускается даже при наличии разрешения,
поэтому короткий учебный цикл повторяет попытку до успеха.
Для обычного блокирующего ожидания проще `acquire()`; активный цикл не является
рекомендацией для длительного ожидания в рабочей программе.

После успеха счётчик уже равен нулю. Вторая попытка возвращает `false`.
Затем ровно один `release()` возвращает забранное разрешение.
Вывод: `First acquired; second: false`.
Дополнительный `acquire()` после успешной попытки стал бы ждать нового разрешения.

Ввод и файлы не нужны; успех — `0`, неожиданный результат — `1`.
Для запуска выберите `main5.cpp`.

## Типичные ошибки

Лишний `release` создаёт лишнее разрешение, забытый — оставляет ожидающих
без прохода. Семафор не возвращает разрешение автоматически при исключении
в вашей работе: для реальной задачи нужен гарантированный путь возврата
(например, RAII-обёртка). Здесь после захвата выполняется короткая демонстрация.
Не уничтожайте семафор, пока другие потоки могут к нему обращаться.
Запрос остановки `jthread` сам по себе не прерывает `acquire()`.
