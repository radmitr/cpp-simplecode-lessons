# 24. `std::osyncstream`

## Версия C++

`std::osyncstream` — **C++20**.
`std::thread`, `std::chrono`, `auto`, лямбды — **C++11**.

Сборка примеров: **C++20**. Это режим проекта,
а не дата появления всех использованных конструкций.

## Что изучаем

Три потока печатают по три сообщения. Каждое сообщение собирается несколькими
операциями `<<`. Если все потоки будут писать напрямую в `std::cout`,
между частями одного сообщения могут появиться части другого.

## Примеры

- [main.cpp](main.cpp).

Выбирайте один исходник с `main()`; варианты запускаются отдельно.

- [main2.cpp](main2.cpp): `emit()`, `flush`, `emit_on_flush`, `noemit_on_flush` и `flush_emit`.

## Как это работает

Внутри каждой итерации создаётся отдельный объект:

~~~cpp
std::osyncstream line(std::cout);
line << "Worker " << id << ": ";
line << "message " << number << '\n';
~~~

Сокращённый фрагмент; полный пример: [main.cpp](main.cpp).

Операции `line << ...` сначала записывают текст в отдельный буфер объекта `line`.
В конце итерации `line` уничтожается и передаёт накопленное сообщение в
`std::cout` целиком. Сообщения, переданные через другие `osyncstream` в тот же
буфер `std::cout`, не вклиниваются внутрь этого текста.
Пауза между операциями `<<` показывает, что даже долго собираемое сообщение
сохраняется целым.

Порядок целых сообщений неизвестен. Должно быть 9 строк Worker
и завершающая строка All 9 messages finished.
`main` выводит последнюю строку обычным `cout` после всех `join()`.

Для этого все потоки, которые печатают одновременно, должны писать через
`osyncstream`, связанный с тем же буфером `std::cout`. Если один поток обойдёт
его и начнёт писать напрямую в `std::cout`, гарантия цельного сообщения
на такую запись не распространяется.

osyncstream защищает передачу вывода. Он не защищает ваши общие переменные
и не заменяет `mutex` вокруг произвольных операций с данными.
Передача текста в `std::cout` не гарантирует немедленного появления на экране:
дальнейший вывод тоже может быть буферизован.

### `main2.cpp`: передача сообщения и сброс буфера

Для наблюдения используется собственный `TrackedBuffer` на основе `stringbuf`.
Он хранит полученный текст и считает вызовы `sync()`.
Это позволяет проверить поведение без предположений о скорости терминала.

1. `message << "A"` записывает только во внутренний буфер `osyncstream`.
2. `message.emit()` передаёт `A` в нижележащий буфер. Сброс ещё не запрошен:
   `flushes == 0`.
3. `message << "B" << std::flush` при настройке по умолчанию только
   запоминает запрос сброса. Снаружи всё ещё видна лишь `A`.
4. Следующий `emit()` передаёт `B` и выполняет отложенный сброс: `flushes == 1`.
5. `std::emit_on_flush` включает передачу при сбросе. Запись `C` и `flush`
   теперь сразу передают текст и вызывают `sync()`.
6. `std::noemit_on_flush` возвращает обычный режим. Манипулятор
   `std::flush_emit` всё равно явно запрашивает сброс и выполняет передачу `D`.

Вывод: `Transferred: ABCD; flushes: 3`.
Сброс нижележащего буфера не гарантирует физическую запись на диск
или немедленную отрисовку терминалом. Атомарно переданный текст тоже
может дальше буферизоваться.

`emit()` не уничтожает `osyncstream`: им можно пользоваться снова.
Деструктор передаст оставшийся текст; явно переданный текст повторно не выводится.
Вариант работает без потоков, потому что изучаем именно управление буфером;
параллельный вывод показан в `main.cpp`.
