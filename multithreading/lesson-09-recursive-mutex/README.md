# 09. `std::recursive_mutex`

`main.cpp` трижды захватывает rm в одном потоке и трижды освобождает его.
Окончательно мьютекс становится доступен другим потокам после третьего `unlock()`.
Функция `foo()` в этом файле не вызывается.

`main2.cpp` запускает `foo(10)` в двух потоках. Каждый рекурсивный вызов `foo()`
снова захватывает rm. Владельцу разрешён повторный захват: `foo(9)` выполняется
в том же потоке, что и `foo(10)`. Но другой поток ждёт полного освобождения rm.

При возврате из рекурсии каждый вызов делает свой `unlock()`,
в том числе базовый случай с a <= 1. Получаются два блока чисел от 10 до 1.

Обычный `std::mutex` нельзя повторно захватывать в уже владеющем им потоке:
это неопределённое поведение, которое может проявляться зависанием.
В комментариях `main.cpp` есть намеренно неверные варианты работы с `mutex`;
не считайте их альтернативными корректными способами синхронизации.

## Почему рекурсия проходит, а второй поток ждёт

rm хранит владельца и глубину его захватов. При вызовах `foo(10)`, `foo(9)`, …
`foo(1)` **один и тот же поток** успешно захватывает rm десять раз.
Это не десять новых потоков. При возврате вызовы освобождают захваты
по одному; только нулевая глубина открывает доступ другому потоку.

Второй `std::thread` имеет другого владельца, поэтому его первый `rm.lock()`
ждёт. Пауза 200 мс перед его созданием делает ожидаемый порядок вероятным,
но не является строгим доказательством того, кто захватит rm первым.

Результат — два отдельных блока 10…1; идентичные числа не показывают,
какой из работников был первым.
Все ветви `foo` должны освобождать свой успешный захват, включая базовый случай.
Для исключений безопаснее локальный `lock_guard<recursive_mutex>`
в каждом рекурсивном вызове.

`recursive_mutex` нужен только при осознанном повторном входе владельца.
Он не решает deadlock двух разных `mutex` и может скрыть слишком сложную
схему вызовов. Часто интерфейс можно разделить на внешнюю функцию с `lock`
и внутреннюю, вызываемую при уже удерживаемой блокировке.
