# Проверка проекта на Linux

Проверено 27 октября 2026 года на Linux: GCC 11.4.0, libstdc++, GDB 12.1, локаль терминала UTF-8.

## Что проверено

- Найдено 175 файлов `.cpp`: 166 самостоятельных программ с `main()` и 9 вспомогательных исходников.
- Все 166 программ собраны с `-std=c++17 -O0 -g -Wall -Wextra -Wpedantic -pthread`, с нужными вспомогательными `.cpp` и путями `include/`.
- Для всех 166 программ отдельно выполнены команды сборки из Linux-настроек задач соответствующего урока. Результаты совпадают с `program` из `launch.json` и задачей `Run (No Build)`. После перехода на единый `build/` в корне проверка повторена; пути из корневой конфигурации и конфигурации урока разрешаются в один файл для каждой программы.
- Все 166 программ запущены с подготовленным вводом. Рабочие каталоги изолированы, учебные `.txt` скопированы во временные папки. Отслеживаемые данные в репозитории не менялись.
- 162 программы завершились с кодом 0. Три примера явно проверяют недопустимый индекс; один содержит бесконечный цикл. Подробности ниже.
- Все 220 JSON-файлов задач и запуска читаются без ошибок. Проверены ссылки `preLaunchTask`, пути Linux-бинарников и GDB.
- GDB остановился на `main()` в STL-уроке 4, затем продолжил выполнение: вывод `10`, `30`, нормальное завершение.
- Общая задача корня `Build and Run` проверена на 8 примерах: обычный урок, имя `main 2.cpp` с пробелом, каталог со скобками, `String`, `SimpleTimer`, оба проекта с `src/` и `include/`, широкий ввод/вывод урока 118. Выбор JSON вместо `.cpp` выдаёт понятную ошибку.
- После перехода на единый `build/` повторно запущены все 166 программ с теми же результатами, проверены `Build and Run` и `Run (No Build)` на 8 примерах корня и 7 примерах отдельных уроков. GDB остановился на точке останова в бинарнике общего `build/`; запись и чтение UTF-8 проверены для всех трёх вариантов урока 118.
- Для Windows проверены выходные пути сборки и запуска, зависимость от создания `build/` и синтаксис Bash-команд. Эти проверки не заменяют запуск на Windows.

Команды задач выполнены из терминала с подстановкой переменных VS Code. Нажатие F5 и интерфейс расширения C/C++ в самом VS Code автоматически не проверялись. Проверка GDB выполнена отдельно; песочница сначала запретила `ptrace`, после разрешения запуск отладчика прошёл успешно.

## Исправления

- `multithreading/lesson-05-class-methods/main2.cpp`: `thread t(&MyClass::doWork, m)` — явный адрес метода класса.
- `multithreading/lesson-05-class-methods/main3.cpp`: `thread t(&MyClass::doWork2, m, 123)` — аналогично для метода с параметром. Без `&` GCC 11 отклонял оба файла. После исправления оба собраны и завершились с кодом 0.
- В задачах уроков многопоточности 6–8 добавлен `SimpleTimer.cpp`; в Linux он также подключается в уроке 10. Linux-сборка использует `-pthread`.
- В 109 парах конфигураций уроков и шаблона добавлены блоки `linux`, переопределяющие компилятор, оболочку, бинарник и отладчик. На обеих платформах выходные пути ведут в единый `build/` в корне; перед компиляцией обычных уроков зависимая задача создаёт нужную папку внутри него. В Windows-задачах уроков 6–8 также исправлен пропущенный `SimpleTimer.cpp`. Сборка и запуск на Windows в этой задаче не выполнялись.
- В корне добавлены общие задачи и запуск для обеих платформ, а также `scripts/build-linux.sh` и `scripts/build-windows.sh`. Они позволяют работать с открытым корнем репозитория, включая многофайловые уроки. Оба скрипта используют C++17; Windows-скрипт нормализует пути через MSYS2 `cygpath`.
- Все результаты текущих задач сохраняют структуру исходников под общим `build/`: например, `build/basics/lesson-118-file-io-fstream/main3` на Linux и тот же путь с `.exe` на Windows. Для уроков 139–140 это `build/basics/<папка урока>/src/main` и `main.exe`. Эти пути одинаковы при открытии корня и отдельного урока. Прежние 109 внутренних каталогов `build/` с результатами прошлых проверок удалены; новых копий и архивов бинарников не создавалось.

## Урок 118 и русский текст

Все три варианта — `main.cpp`, `main2.cpp`, `main3.cpp` — проверены на чистых временных файлах:

- меню отображается как UTF-8;
- запись русского текста создаёт ожидаемые байты UTF-8;
- повторный запуск читает записанный текст;
- файл с UTF-8 BOM читается; широкий вариант использует `consume_header`;
- ввод буквы вместо пункта меню возвращает код 1 и сообщение об ошибке.

`main.cpp` сохраняет одно слово; `main2.cpp` и `main3.cpp` — строку с пробелами. Для широкого варианта на этой машине достаточно существующего `std::setlocale(LC_ALL, "")`: менять его Linux-ветку не понадобилось.

Отслеживаемый `myFile.txt` урока 118 содержит 6 нулевых байтов в 34 байтах. Он сохранён как есть. Для проверки нового текста использовались отдельные файлы; необычный вид старых записей сам по себе не означает ошибку кодировки консоли.

## Предупреждения и ограничения

Сборка выдала 16 предупреждений: 13 о неиспользуемых переменных/параметрах, 2 об устаревшем `auto_ptr`, 1 о передаче строкового литерала в `char*` в уроке 139. Предупреждения оставлены видимыми. Для устранения последнего параметр `MyClass::printMessage` следует сделать `const char*` в объявлении и определении.

Режим C++17 выбран для установленного GCC 11: он не принимает `-std=c++26`. Старые учебные примеры с `auto_ptr` и `random_shuffle` собираются здесь благодаря совместимости libstdc++ с устаревшими возможностями; это не гарантия сборки другой стандартной библиотекой или будущим компилятором. `codecvt` в уроке 118 также требует отдельного рассмотрения при переходе на новые стандарты.

Проверка охватывает сборку, один основной сценарий запуска каждой программы и отдельные сценарии UTF-8. Она не доказывает корректность всех алгоритмов, всех вариантов ввода или отсутствие ошибок памяти и гонок данных. Порядок вывода потоков может меняться при каждом запуске.

Локальные подробные результаты и логи находятся в игнорируемом каталоге `build/linux-check/`, результаты текущей проверки единого каталога — в `build/linux-check/single-root-build/`. Это локальные материалы проверки, не исходные файлы проекта.
